# 文档优先开发流程

## 四层文档职责

| 层次 | 回答的问题 | 内容边界 |
| --- | --- | --- |
| [intent](intent/README.md) | 用户为什么需要、希望得到什么？ | 产品目标、用户故事、公开配置示例、预期行为；不承载 DOM 选择器和工程接入方案 |
| [architecture](architecture/README.md) | 系统如何划分职责、保证行为？ | 系统边界、职责分层、核心链路、核心数据结构及行为契约；具体改动方案放 plan |
| [plan](plan/monkey.md) | 本次如何把需求落成代码？ | 需求依据、当前差异、技术方案、步骤、依赖、验收范围与方法；不记录执行日志 |
| [reference](reference/README.md) | 上游实际提供什么、证据是什么？ | 来源、核查时间、环境、观察事实、限制与未核查项；不把平台观察直接当作产品承诺 |

代码和测试实现并验证需求与架构契约。仓库 README 面向项目入口与开发说明；内部应用不单独维护 README，实施与验收方案归入 plan，平台核查归入 reference；编码与测试规则分别集中在 [code-style](code-style.md) 和 [testing](testing.md)。索引负责导航，流程规则集中在本文。

## 文档写法

- intent 从用户目标出发，通过目录、TOML 和预期操作结果表达需求。不为迁就实现而缩减需求。稳定设计归入 architecture，实施方案归入 plan，平台观察归入 reference，保留用户可见的配置规范。
- architecture 以真实代码为基线，沿连续的业务链路说明职责、输入输出与协作关系。相关数据结构在创建、使用和传递的链路中解释，不将底层配置到 UI 状态的所有类型集中在一篇文档。可以使用真实类型、接口和必要代码片段说明设计，不另造概念类型替代实现，也不逐文件复述代码。具体改造方案和待解决差异放 plan，平台事实放 reference。
- plan 直接维护已有实现方案。已确认设计与原计划冲突时修改对应章节，不另建重复计划，也不把冲突堆成变更记录。写明目标、范围、方案及验收方法和通过标准，稳定契约同步 architecture；不保留执行过程、验证结果或交付日志。
- reference 区分观察、推断和未核查。记录账号权限、路由、浏览器、脚本版本等适用条件；局部确认、当前表单读回、最终保存分别表达。

## 变更顺序

1. **理解意图**：阅读相关 intent，再核对架构、计划、上游证据、代码和测试，确定范围与差异。
2. **明确需求**：新增或改变用户行为时先更新场景与预期结果；修复和内部重构保持原始意图稳定。
3. **修订方案**：涉及模块边界、跨模块流程或平台能力时，在已有计划对应章节更新方案、依赖和验收；简单文案或局部修复按影响范围维护相关内容。
4. **实现与验证**：按计划实现，验证用户行为、失败路径和资源清理。涉及平台假设时先核查或明确保留未验证状态。
5. **同步规范**：更新有效架构契约、实施与验收方案、上游参考和使用说明。执行结果在任务反馈或 PR 中报告，不写入规范与计划文档。

## 冲突处理

需求、架构、计划与代码不一致时，先判断用户意图是否改变。意图未变则调整方案或实现；意图改变则先更新 intent。上游限制可以解释当前未完成范围，不能自动改写用户目标。无法确认预期行为时，列出具体冲突并向需求提出者确认，其他独立工作继续推进。

## 完成条件

- 用户目标及改变后的预期行为清晰，方案能追溯到对应需求。
- 架构、代码、类型与测试一致；计划明确验收范围、方法与通过标准。
- 操作变化同步使用说明；平台结论有来源和适用边界。
- 运行适用检查并报告结果；纯开发文档修改检查事实、链接与 `git diff --check`。
- 移动或删除文档时修复引用；避免多份文档重复维护同一规范。
