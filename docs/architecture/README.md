# 架构设计

Bilipack 将用户准备的视频包转化为当前稿件的投稿准备操作，并以页面证据反馈结果，最终提交由用户完成。本目录说明支撑这一目标的系统设计：职责如何分层，数据如何流动，执行如何受到约束。

产品目标和公开配置规范以 [intent](../intent/README.md) 为依据；具体代码改造放在 [plan](../plan/monkey.md)，平台事实及证据放在 [reference](../reference/README.md)。架构以真实代码为基线，使用实际类型、接口和必要代码说明设计；章节围绕职责、核心链路与数据契约组织，不逐文件复述实现。

## 设计主线

```text
用户准备的视频包
       ↓
输入校验与领域解释 → 可执行目标
       ↓
流程编排 ↔ 平台适配 ↔ 当前稿件的原生页面
       ↓
核验结果与人工接手信息 → 用户检查并提交
```

系统以一次导入、一个稿件、一个视频为工作范围。配置表达期望，页面提供现实状态，编排层协调两者；三者不能互相替代。

## 长期设计约束

- 用户显式配置决定修改范围，未配置内容保持原状。
- 先验证输入和执行条件，再修改页面；平台能力不反向定义配置语义。
- 页面操作与业务编排分离，完成结论必须来自核验证据。
- 异步操作始终属于同一稿件上下文，失效后不能继续写入。
- 失败保留现场，最终投稿、存草稿和保存修改由用户控制。

上述约束用于评审设计和发现偏离。需求、架构与实现的差异通过 [计划](../plan/monkey.md) 明确调整方案与验收范围，不能将现有实现直接提升为需求。
