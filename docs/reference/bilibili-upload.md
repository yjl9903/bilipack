# B 站投稿页面能力核查

核查时间：2026-10-04～05（Edge）、2026-10-19（Chrome）。来源为 Tampermonkey 开发脚本对真实页面的观察与交互核查，不是平台官方规范。以下结论限于观察到的账号、路由和页面版本；页面结构与权限变化后需重新核查。

## 页面结构与视频状态

| 场景 | 观察到的结构或行为 |
| --- | --- |
| 新投稿 | 路由为 `https://member.bilibili.com/platform/upload/video/frame`；主表单是顶层文档中唯一的 `#video-up-app`，外层为 `micro-app-body#video-up`，不在页面的消息等 iframe 内 |
| 未选择视频 | 已有 `#video-up-app`，但没有标题框和视频任务；上传区域为 `.video-entrance .upload-wrp`，隐藏的多选视频 input 位于 `.bcc-upload-wrapper`，accept 以 `.mp4,` 开头 |
| 已选择视频的新投稿 | 视频任务位于 `.upload-queue .task`；`.task-status .text` 可显示「上传中...」「上传完成」，文件状态也可显示「上传完成」；视频 input 为 `input[type=file][name=buploader]` |
| 已发布编辑 | 路由带 `type=edit&bvid=BV…`；观察到单视频页面没有上传队列 task，以唯一 `.file-item`、`.title-text` 和 `.file-item-content-status .success` 表示已有视频及上传完成 |
| 投稿等待提示 | `.auto-complete-container-v2` 可在正常表单中提前挂载并隐藏；`textContent` 包含的等待文案不代表页面正在等待自动提交，应结合实际可见文字与标题框可见性判断 |

真实新投稿中，向原生视频控件分配 FileList 并触发 change 已被接受，页面出现对应视频任务并最终显示上传完成。此结论仅覆盖单视频成功上传；多 P、失败状态和自动提交全过程未核查。

## 2026-10-19 Chrome 新投稿字段复核

环境为用户已安装的 Tampermonkey dev 脚本、Vite 本地服务和 Chrome 新投稿页。使用自行生成的三秒蓝色视频及短 SRT 测试文件；原生页面显示上传完成。先通过 DevTools 调用本地开发适配器操作可见原生控件，再用 Bilipack 面板选择测试目录、比对并写入；不访问平台私有组件状态或投稿 API。以下是未提交表单证据。

| 项目 | 目标、实际状态及接受性 | 约束或失败证据 |
| --- | --- | --- |
| 定时时间 | `2026-10-20T10:30:00Z` 读回同一时间点，页面北京 18:30；跨月至 `2026-11-01T02:45:00Z` 读回一致；负偏移 `2026-10-21T04:15:00-04:00` 对应北京 16:15 | 页面提示最早 5 分钟、最晚 15 天；月导航也会改变选中日期/时间，必须再选择目标日和时分 |
| 时区与时分 | 主输入框是 `.bcc-select-input-inner`，展开后另有搜索输入框；GMT 读回保持同一时间点。原生小时 00～23、分钟每 5 分钟一项 | 18:31 无对应菜单项，明确失败而不取整；非零秒/小数秒在操作前拒绝。日历 `.next-btn-day` 切换日，`.next-btn-month` 切换月，不能按箭头外观推断 |
| 话题 | 搜索精确选择「上B站看播客」、替换为「电台新星征集令」、重复选择及清空均读回一致；保留原有普通标签 | 本地确认后话题成为带 `.topic-icon` 的标签项，占一个名额；普通标签不得将它当作多余标签删除 |
| 普通标签 | 有话题时，普通标签目标「生活记录、学习、记录」收敛并读回一致，话题保持；替换/清空话题后普通标签保持 | 本次「测试」标签两次等待未被接受，适配器报告未收敛并保留实际标签；原因未确认，不据此宣称所有标签均可写入 |
| 已有合集 | 当前账号可选的一个已有合集按精确名称选择、清除后再选，均读回一致 | 不存在名称报告匹配 0 项，关闭本次打开的菜单；未创建或保存合集 |
| 杜比、Hi-Res | 两个复选框分别关闭/开启均读回一致，也可同时开启 | 仅证明表单接受，未验证转码后媒体效果或平台最终资格审核 |
| 商业推广 | 开启读回 true，出现「花火官方合作」「其他」；关闭读回 false | 默认面板要求入驻花火接单或在其他页录入备案。仅配置 enabled 不足以确认资料完成，结果保留人工待处理 |
| 禁止转载、全景视频 | 展开更多设置后仍无独立可识别控件；切换「内容为转载」出现来源输入，但无禁止转载开关，随后恢复原声明 | 不将创作声明替代禁止转载，也不把控件缺失读成 false；两项显式跳过 |

Chrome 原生点击 Bilipack「写入配置」时，点击继续冒泡可关闭刚打开的定时菜单，表现为菜单等待超时且时间未改；控制台直接调用不能复现同一事件链。面板写入按钮隔离点击冒泡，并在自有 UI 测试验证源站外部点击监听不会收到该事件。修复后再次用 Chrome 原生点击「写入配置」，校验清单中定时开关、时间、话题、合集、两种音质、普通标签及英日字幕均核验成功，无执行失败；商业资料为待核验，禁止转载与全景视频明确跳过。

定时、话题、合集菜单只在本次打开后负责关闭，精确匹配失败保留已完成操作及可读原因。上述字段复核只覆盖新投稿和同页恢复的未提交视频，不扩展已发布编辑页的验证范围。

## 2026-10-19 合集更新推送补充核查

用户调整配置范围后，禁止转载和全景视频已从配置定义移除；上节关于跳过的记录仅描述移除前的核查，不代表当前仍可配置。

同一 Chrome 新投稿测试表单中，加入已有合集后出现 `.video-season .bcc-checkbox`，标签为“此稿件不生成更新推送”，状态由原生 checkbox 的 checked 读回。配置采用正向 `publish.collection_update_push`：false 写入后 checked=true、读回 false；再次写入 false 保持不变；true 写入后 checked=false、读回 true。以上两个方向均经适配器核验一致。

通过 Bilipack 面板导入仅含非空 `publish.collection` 的测试配置，在原生“不生成更新推送”已勾选时执行，默认目标 true 取消了勾选；校验清单显示“合集”和“合集更新推送 是”均完成。未选择合集时该控件不显示；配置校验要求推送字段必须伴随非空合集，执行依赖要求合集先核验成功。依赖失败的阻断通过 mock 流程测试验证，不作为平台实测结论。

本次仅验证开发脚本中的未提交表单；未点击投稿、存草稿或保存修改，未验证实际推送发送或已发布编辑页。

## 封面编辑器

| 项目 | 已核查的平台含义或行为 |
| --- | --- |
| 两个比例 | 同一编辑器提供个人空间封面 16:9、首页推荐封面 4:3 两个槽位 |
| 原图比例 | 平台可接收不同于目标比例的原图，并在编辑器中裁剪；要求输入文件预先符合目标比例不是平台限制 |
| 尺寸提示 | 4:3 页面建议至少 1200×900，实际 960×720 也被接受；建议值不能据此认定为硬性下限 |
| 打开编辑器 | 点击 `.cover-img` 或 `.cover-empty` 子元素可触发原生处理，点击外层 `.cover-slot` 未触发 |
| 比例与同步控件 | 比例选择由 upper-canvas 的鼠标事件激活；同步 checkbox input 隐藏，可在可见 label 中读取 checked |
| 同步原图 | 开启双比例同步后，可上传一次原图并分别调整两比例裁剪位置；横图、竖图均观察到独立构图保留 |
| 同步开关联动 | 切换任一比例的同步 checkbox 会同时更新两个开关，局部确认后重开仍保持该状态 |
| 独立双图 | 关闭同步后，在同一编辑器会话分别上传两个文件，统一点击 `.cover-editor-button .submit`「完成」，两比例可保留不同图片 |
| 分次确认 | 逐张确认可能触发「检测到另一个比例未修改」的同步提示，确认同步可能覆盖另一比例 |
| 重复上传 | 同图重传可能像素不变，不能仅凭像素变化判断文件事件是否被接受；新增 blob 预览 URL、图像加载和稳定画布可提供辅助信号 |

裁剪位置与缩放是不同操作。已核查默认适配缩放下的居中、裁剪范围两端及不同偏移；同步上传不要求两比例采用相同裁剪位置。

核查覆盖新投稿与已发布编辑表单的原图同步裁剪、独立双图及重开读回。重开后的画布采样、裁剪几何和同步状态一致，只证明局部确认后的当前表单状态；不证明与输入图片逐像素一致，也不证明最终存档或公开展示一致。

尚未核查最终投稿／保存后的刷新读回、EXIF 方向、大图边界、更多编码组合及失败恢复。

## 字幕入口与更新语义

- 新投稿表单存在「上传字幕」入口，弹窗为 `.subtitle-upload .bcc-dialog`，支持 SRT，默认语言为中文。
- 页面说明单 P 稿件可直接上传 SRT；分 P 稿件需在投稿后前往播放页上传字幕。分 P 流程未实际核查。
- 原生「上传文件」按钮会在同步 click 过程中创建并点击脱离 DOM 的文件 input；静态查询页面中的 input 无法可靠找到它。
- 已有字幕语言的下拉项提示不可重复选择，需要删除后重新添加。中文 SRT 的新增、移除后替换、局部确认及重开读回已核查。
- 弹窗局部确认后，当前表单可显示已上传的中文语言标记；语言和文件名读回不证明平台保存的字幕正文一致，也不证明稿件已最终提交。
- 2026-10-19 Chrome 补充：配置「英语」映射原生 `English`，配置「日语」映射原生 `日本語`；两种语言的新增、移除后替换、局部确认和重开按语言/文件名读回均通过，替换一项后另一语言保留。
- 页面摘要使用 `【En】`、`【日本】`，与语言菜单名称不同。旧实现按完整语言名等待摘要会在已上传后超时；改为确认修改入口存在，再重开字幕弹窗核验，不能单靠摘要缩写判定。
- 已发布视频编辑页的字幕流程及中文、英语、日语以外的语言未核查，不能由已核查路径推断其行为。

## 核查结论的适用范围

普通字段读回、视频上传完成、附件局部确认与稿件最终提交是不同状态。已有编辑表单在未保存时刷新恢复原值，只说明修改尚未最终提交。

上述核查使用已安装的开发脚本；Chrome 新投稿已按本次补充范围核查，正式打包产物重新安装仍未核查。DOM 结构观察不单独证明事件接受性，本地模拟测试也不能代替真实页面核查。

## 长操作期间上下文变化的核查边界

当前代码为普通字段、封面和字幕操作加入了绑定稿件、页面代次、终止信号及投稿等待检查。这属于实现契约；mock 操作及通用 DOM 控件测试不能证明 B 站长操作中的实际事件时序。真实页面仍需复核：封面裁剪或字幕上传等待期间切换稿件、进入平台投稿等待后停止后续写入，以及同稿件视频完成等待继续观察。不得由本地通过推断当前表单、正式安装或最终保存已验证；最终投稿、存草稿及保存修改仍由用户操作。
